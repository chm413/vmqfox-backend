# EPay 商户接入与运营

> 适用版本：V3.4 起。本文面向**运营者**（开商户、轮换密钥）与**接入方**（对接下单与回调），内容与代码保持一致：
> 协议实现见 `internal/domain/epay/`，管理端接口见 `internal/http/handler/merchant.go`，签名规则见 `internal/domain/epay/sign_v1.go`。

## 1. 这个功能是什么

平台扮演 EPay 支付平台：你在管理端为每个接入方开一个**商户号**，接入方用它在自己的系统里发起下单、接收异步回调。与独角数卡等主流 EPay 插件兼容（V1 协议）。

- 订单与原生 VMQ 订单同库不同源：`orders.protocol = 0` 是原生单，`1 = EPay V1`，`2 = EPay V2`。
- 商户密钥在库里以 AES-256-GCM 加密存储（AAD 绑定商户与协议），**明文只在创建/轮换的那一次响应里出现**。

## 2. 开通一个商户（运营）

1. 管理台 → **商户管理** → 新建商户；
2. 填名称、订单有效期、备注；
3. 提交后会弹出**一次性密钥窗口**：`商户号（pid）` + `商户密钥`。**当场复制给接入方**，关闭后无法再查看；
4. 接入方把这两项填进他们的 EPay 配置，即可开始下单。

> 密钥丢失只能**轮换**。轮换会让接入方旧配置立即失效（旧密钥只用于验证历史请求）。

### 订单有效期的语义（重要）

| 设置 | 实际行为 |
| :--- | :--- |
| `close_minutes = 0` | 跟随系统全局配置（系统设置 → 订单有效期） |
| `close_minutes = N` | 该商户的订单 N 分钟后自动关单，**与全局配置无关** |

后台看板上的全局值只是默认值。EPay 商户常需要更长的有效期（如 30 分钟，覆盖"转账到账延迟"），
设置过短会导致**钱到了、单已经关了**——这类订单只能人工核对，务必按接入方的实际结算速度设置。

## 3. 接入方对接（V1）

### 3.1 三个入口

| 方法 | 路径 | 用途 |
| :--- | :--- | :--- |
| GET | `/submit.php` | 页面跳转下单（浏览器直接打开） |
| POST | `/mapi.php` | API 下单，返回 JSON（含 `payurl`/`qrcode`） |
| GET | `/api.php?act=order` | 查询单笔订单状态 |

> 三个入口都挂在**根路径**，不带 `/api` 前缀——EPay 插件是按 `<网关域名>/submit.php` 拼地址的。

### 3.2 签名规则

1. 剔除 `sign`、`sign_type`（**参数名精确小写匹配**，`Sign`/`SIGN` 这类变体一律拒绝而不是当普通参数）；
2. **剔除值为空串的参数**——空串 ≠ `"0"`，`"0"` 与 `"0.00"` 必须保留；
3. 参数名按 **ASCII 升序**排列（等价 PHP 的 `ksort`）；
4. 拼成 `k1=v1&k2=v2&...`，**值保持原样：不做 URL 编码、不 trim**（签名域用解码后的原始值，组装发送串时才 urlencode）；
5. 末尾直接拼上商户密钥：`...&k=v` + `key`（中间无分隔符）；
6. `sign = md5(...)` 小写 32 位，随请求回传 `sign` 与 `sign_type=MD5`。

### 3.3 参数约束（会被拒绝的输入）

| 输入 | 结果 | 说明 |
| :--- | :--- | :--- |
| 参数值里含 `&` | 返回「签名错误」 | 签名域对解码后的值不是单射：`{a:"1&b=2"}` 与 `{a:"1",b:"2"}` 会拼出同一个待签串与同一个 MD5，等于**一个签名授权两条不同记录**。代价是带多个查询参数的 `notify_url` 无法接入 |
| 值里含控制字符（`\n`、`\r`、`\t`、`\0` 等） | 返回「签名错误」 | 日志注入与响应头注入的基本盘 |
| 参数名里含 `&` 或 `=` | 返回「签名错误」 | 同上 |
| 同名参数出现两次 | 返回「签名错误」 | 防「Go 取第一个 / PHP 取最后一个」的解析差异被利用 |

**规避方式**：`notify_url`/`return_url` 只带路径，业务状态放进单个 `param`（自行 URL 编码后再放入）。

### 3.4 异步回调

支付成功后，平台以 **GET** 请求接入方的 `notify_url`，携带：

```
pid, trade_no, out_trade_no, type, name, money, trade_status, param, sign, sign_type
```

- `trade_no` 是平台订单号，`out_trade_no` 是接入方自己的订单号（**对账主键**）；
- `money` 回的是**下单金额**（`price`），不是实际到账金额——金额微调是平台内部核销手段，接入方记账请以自己下的金额为准。

- 接入方处理成功必须返回**纯文本 `success`**（HTTP 200），其它响应视为失败；
- 失败会重试并最终进入死信，管理台可用订单页的「补单」重新投递；
- 回调地址必须是**公网可达的 HTTPS**：内网地址、回环地址、云元数据地址一律拦截（SSRF 防护三层，含 DNS Rebinding）。

### 3.5 V2 协议（RSA 双向签名）

V2 与 V1 的差异只有三处：**签名算法（SHA256withRSA）、`timestamp` 参与签名、报文编码（Base64）**。

开通与对接：

1. 管理端「新建商户」时把协议选为 **EPay V2**，粘贴**商户自己的公钥**（PKIX PEM，`-----BEGIN PUBLIC KEY-----`，
   2048 位以上）。私钥由商户保管，**不要发给我们**。
2. 创建成功后拿到**平台公钥**，商户把它配进自己的面板，用于验证我们的响应与回调。
3. 商户下单时：参数集与 V1 相同，额外带 `timestamp`（10 位秒级），
   用**商户私钥**做 SHA256withRSA 签名，`sign` 为 Base64，`sign_type=RSA`。
4. 我们返回的响应（`mapi.php` / `api.php?act=order`）与回调都会带 `timestamp` 和平台私钥签名。

**响应与回调的签名域**（接入方验签时按这个重建，别把整个 JSON 直接排序）：

| 报文 | 参与签名的字段 |
| :--- | :--- |
| `mapi.php` 响应 | `code`、`trade_no`、`payurl`、`qrcode` + `timestamp` |
| `api.php?act=order` 响应 | `code`、`pid`、`trade_no`、`out_trade_no`、`type`、`name`、`money`、`trade_status`、`addtime`、`endtime`、`param` + `timestamp` |
| 异步回调 | `pid`、`trade_no`、`out_trade_no`、`type`、`name`、`money`、`trade_status`、`param` + `timestamp` |

空值字段不参与签名（与本项目 V1 的待签串规则一致），`sign`/`sign_type` 永远排除。

> 时间戳窗口是 **±300 秒**：超窗的请求即使签名正确也会按「签名错误」拒绝。
> 商户服务器必须做 NTP 对时，偏差超过 5 分钟会表现为「签名错误」，极易误判成密钥配错。

**轮换**：V2 商户轮换会重新生成平台密钥对，商户要换成新的平台公钥；
商户自己换密钥对时，在管理端「编辑商户」里更新商户公钥即可，不需要轮换平台密钥。

### 3.6 对账

`GET /api.php?act=order` 返回订单状态，`trade_status=TRADE_SUCCESS` 表示已支付。
建议接入方以自己的 `out_trade_no` 为主键对账，回调可能重试，**必须幂等**。

## 4. 密钥轮换（运营）

- 入口：商户管理 → 对应商户的钥匙图标 → 选协议 → 确认；
- 轮换后立刻生成新密钥，**新请求必须用新密钥**；
- 旧密钥按代次保留，仅用于验证历史请求的签名；
- 操作会写审计日志（`event=epay.key.rotate`，含商户号与末 4 位指纹，**不含明文**）；
- 建议：轮换前先通知接入方，安排在低峰期，双方确认后再切换。

## 5. 已知限制

| 限制 | 影响 | 现状 |
| :--- | :--- | :--- |
| 参数值不能含 `&` | 带多查询参数的 `notify_url` 无法接入 | 协议级约束，替代方案见 3.3 |
| V2 需商户提供公钥 | 没有公钥无法开通 V2 | 已开放：创建时选 V2 并粘贴商户公钥（PKIX PEM，≥2048 位 RSA） |
| 商户级配额未实现 | 同一金额空间的并发受全局限制；热门价位理论上可被单商户占满 | 设计 §3.4 的 4 项配置仍在排期 |
| 关单批次上限 | 同一时刻 ≥100 笔"长窗口且未到期"订单时，更年轻的已到期短窗口订单可能延后关闭 | 容量到该量级需改为 SQL 下推过滤 |

## 6. 排障对照

| 现象 | 可能原因 | 处理 |
| :--- | :--- | :--- |
| 下单返回「签名错误」 | 密钥不对 / 参数顺序错 / 值里含 `&` 或控制字符 / 重复参数 | 按 3.2、3.3 逐项核对；服务端审计日志可区分"参数被拒"与"密钥配错" |
| 返回「商户不存在」 | `pid` 填错，或商户被停用 | 商户管理页核对商户号与启用状态 |
| 返回「接口未开通」 | `act` 参数不是 `order` | 检查请求 |
| 付款成功但没收到回调 | 回调地址不可达 / 非 HTTPS / 被 SSRF 拦截 / 接入方没回 `success` | 订单页看通知状态，必要时「补单」；确认地址公网可达且返回纯文本 success |
| 钱到了但订单已关闭 | 商户有效期设置短于实际到账时间 | 调大该商户的 `close_minutes`，并人工核对已关闭订单 |

## 7. 安全须知

- 商户密钥等价于该商户的下单权限，按密码管理：不入库明文、不进聊天记录、不进工单系统；
- 管理端响应里带明文的接口（创建/轮换）已加 `Cache-Control: no-store`，不要用会缓存的中间层；
- 平台不接受商户自助注册，所有商户由运营者手工开通，开通与轮换都有审计日志可查。
