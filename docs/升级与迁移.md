# 升级与迁移

## 与旧 PHP 版的关系

> [!IMPORTANT]
> V3.0（Go-only）**不迁移、不读取、亦不兼容**旧版 ThinkPHP 服务端的数据结构。从 PHP 版迁移等同于全新部署：新建空库后执行 `./vmqfox-api -init-admin`（自动建表并初始化管理员，无需导入 `database/schema.sql`），再重新配置通讯密钥。

## 公开订单令牌迁移（Go-only 旧库升级必做）

新版本以 **64 位小写十六进制 `publicToken`** 作为匿名收银台凭据，并**立即停用旧 `orderId` 公开链接**。

> [!WARNING]
> 先在维护窗口运行迁移并确认成功，再同时发布后端与前端。旧订单号支付链接会失效，不能作为新版本的兼容入口。

### 命令

```bash
# 已构建二进制：读取 .env 后执行可重复（幂等）迁移
./vmqfox-api -migrate-public-tokens

# Docker Compose：保持 MySQL 已启动，但在新 API 对外启动前运行一次性迁移容器
docker compose up -d mysql
docker compose run --rm --no-deps vmqfox-api /usr/local/bin/vmqfox-api -migrate-public-tokens
```

迁移会安全地：添加 `orders.public_token` 列 → 分批回填随机令牌 → 创建唯一索引 → 设置非空约束。重复执行不会改写已有效的令牌。

### 迁移后核验

```sql
-- 全部应为非空、唯一的 64 位小写十六进制值
SELECT COUNT(*) total,
       SUM(public_token REGEXP '^[0-9a-f]{64}$') ok,
       COUNT(DISTINCT public_token) uniq
FROM orders;
```

`total = ok = uniq` 即通过，随后再启动/更新 API 与前端服务。

## V3.3（EPay 多商户）升级步骤

> [!WARNING]
> V3.3 给 `orders` 增加了 4 个带默认值的列，并把 `pay_id` 的全局唯一索引换成 `(merchant_id, pay_id)`。
> **新版二进制连旧库会直接报 `Unknown column`（建单 500）**，必须先在维护窗口执行迁移，再启动新版本。

### 1. 备份并确认是旧库

```bash
mysqldump -h "$VMQ_DB_HOST" -u "$VMQ_DB_USER" -p "$VMQ_DB_NAME" > backup-$(date +%F-%H%M).sql
```

```sql
-- 应能查到 uq_orders_pay_id，且 orders 上没有 merchant_id 列
SHOW INDEX FROM orders WHERE Key_name = 'uq_orders_pay_id';
SHOW COLUMNS FROM orders LIKE 'merchant_id';
```

### 2. 执行迁移（幂等，可重复执行）

```bash
# 已构建二进制
./vmqfox-api -migrate

# Docker Compose：先起 MySQL，用一次性容器跑迁移，再启动新 API
docker compose up -d mysql
docker compose run --rm --no-deps vmqfox-api /usr/local/bin/vmqfox-api -migrate
```

迁移会：建 `merchants` / `merchant_keys` → `orders` 加 4 列 → 切换唯一索引为 `(merchant_id, pay_id)`。
索引切换在单条 `ALTER` 内完成（DROP + ADD 原子执行），不会出现"无唯一约束"的窗口。

### 3. 配置主密钥（仅接入 EPay 商户时需要）

```bash
openssl rand -base64 32     # 填入 VMQ_MASTER_KEY
```

未配置不影响原生 `/api/order/create`；但在管理端创建第一个 EPay 商户或轮换密钥时会被拒绝并提示。
Docker 部署注意：`docker-compose.yml` 的 `environment` 是显式白名单，需自行补 `VMQ_MASTER_KEY` 透传。

### 4. 启动与核验

```sql
SHOW INDEX FROM orders;
-- 期望：存在 uq_orders_merchant_pay_id，且不再有 uq_orders_pay_id
```

- `GET /health`、`GET /ready` 正常；
- 用原生协议下单一次，确认 `merchant_id=0` 落库；
- 管理端登录、监控端在线状态正常。

### 5. 回滚边界

- **加列可回滚**（`DROP COLUMN`），但会丢失 `merchant_id`，此后 EPay 订单无法正确签名；
- **索引切换不可回滚**：一旦已有两个商户使用相同 `out_trade_no`，重新加全局唯一索引必然 1062；
- 最稳妥的回滚方式是恢复升级前的备份。

## 版本升级通用步骤

1. 备份数据库：`mysqldump ... > backup-$(date +%F).sql`。
2. **先**比对 `.env` 与新版 `env.production.example`，补齐新增变量（如 V3.0 的 `VMQ_SERVER_*_TIMEOUT`、
   V3.3 的 `VMQ_MASTER_KEY`）。顺序不能反：先启动再补变量，中间那段就是宕机窗口。
3. 拉取新版本 / 替换二进制（或 `docker compose pull`）。
4. 涉及数据库结构变更时**先**执行迁移命令（V3.3 起统一为 `./vmqfox-api -migrate`，幂等），再启动服务。
5. 启动/更新服务（`docker compose up -d`）。
6. 校验 `/health`、`/ready`，登录管理台确认监控端在线状态正常。
