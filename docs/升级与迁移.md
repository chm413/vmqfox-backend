# 升级与迁移

## 与旧 PHP 版的关系

> [!IMPORTANT]
> V3.0（Go-only）**不迁移、不读取、亦不兼容**旧版 ThinkPHP 服务端的数据结构。从 PHP 版迁移等同于全新部署：新建空库后执行 `./vmqfox-api -init-admin`（自动建表并初始化管理员，无需导入 `database/schema.sql`），再重新配置通讯密钥。

## 公开订单令牌迁移（Go-only 旧库升级必做）

新版本以 **64 位小写十六进制 `publicToken`** 作为匿名收银台凭据，并**立即停用旧 `orderId` 公开链接**。

> [!WARNING]
> 先在维护窗口运行迁移并确认成功，再同时发布后端与前端。旧订单号支付链接会失效，不能作为新版本的兼容入口。

### 命令

```bash
# 已构建二进制：读取 .env 后执行可重复（幂等）迁移
./vmqfox-api -migrate-public-tokens

# Docker Compose：保持 MySQL 已启动，但在新 API 对外启动前运行一次性迁移容器
docker compose up -d mysql
docker compose run --rm --no-deps vmqfox-api /usr/local/bin/vmqfox-api -migrate-public-tokens
```

迁移会安全地：添加 `orders.public_token` 列 → 分批回填随机令牌 → 创建唯一索引 → 设置非空约束。重复执行不会改写已有效的令牌。

### 迁移后核验

```sql
-- 全部应为非空、唯一的 64 位小写十六进制值
SELECT COUNT(*) total,
       SUM(public_token REGEXP '^[0-9a-f]{64}$') ok,
       COUNT(DISTINCT public_token) uniq
FROM orders;
```

`total = ok = uniq` 即通过，随后再启动/更新 API 与前端服务。

## V3.4（EPay 多商户 + 管理端商户界面）升级步骤

> [!WARNING]
> V3.4 给 `orders` 增加了 4 个带默认值的列，并把 `pay_id` 的全局唯一索引换成 `(merchant_id, pay_id)`。
> **新版二进制连旧库会直接报 `Unknown column`（建单 500）**，必须先在维护窗口执行迁移，再启动新版本。
>
> 已在两个环境实测：CI 的 MySQL 5.7 容器、以及一台 Ubuntu 24.04 + MySQL 8.0.46 真机。
> `-migrate` 重复执行会输出「无待应用迁移」，可安全重跑。

### 0. 初始化与升级的顺序（最容易搞反）

| 场景 | 顺序 |
| :--- | :--- |
| **全新安装** | `-init-db`（建表）→ `-migrate`（应用 001/002/003）→ 启动 |
| **已有 Go-only 旧库升级** | 备份 → `-migrate` → 启动（旧库已有表，**不要**再跑 `-init-db`） |

`-migrate` 检测到 `orders` 表不存在会直接报错并提示「请先用 -init-db 初始化基础表结构」——
这是刻意设计的，避免在半初始化状态上做迁移。

### 1. 备份并确认是旧库

```bash
mysqldump -h "$VMQ_DB_HOST" -u "$VMQ_DB_USER" -p "$VMQ_DB_NAME" > backup-$(date +%F-%H%M).sql
```

```sql
-- 应能查到 uq_orders_pay_id，且 orders 上没有 merchant_id 列
SHOW INDEX FROM orders WHERE Key_name = 'uq_orders_pay_id';
SHOW COLUMNS FROM orders LIKE 'merchant_id';
```

### 2. 执行迁移（幂等，可重复执行）

```bash
# 已构建二进制
./vmqfox-api -migrate

# Docker Compose：先起 MySQL，用一次性容器跑迁移，再启动新 API
docker compose up -d mysql
docker compose run --rm --no-deps vmqfox-api /usr/local/bin/vmqfox-api -migrate
```

迁移会：建 `merchants` / `merchant_keys` → `orders` 加 4 列 → 切换唯一索引为 `(merchant_id, pay_id)`。
索引切换在单条 `ALTER` 内完成（DROP + ADD 原子执行），不会出现"无唯一约束"的窗口。

### 3. 配置主密钥（仅接入 EPay 商户时需要）

```bash
openssl rand -base64 32     # 填入 VMQ_MASTER_KEY
```

未配置不影响原生 `/api/order/create`；但在管理端创建第一个 EPay 商户或轮换密钥时会被拒绝并提示。
> [!CAUTION]
> **主密钥必须离线备份，与数据库备份分开存放。** 主密钥丢失后，`merchant_keys` 里的商户密钥无法解密：
> 所有 EPay 商户的验签会全部失败，只能逐个重新轮换密钥并让商户改配置——已有订单不受影响，但停机时间取决于商户响应速度。

Docker 部署：`docker-compose.yml` 已显式透传 `VMQ_MASTER_KEY` 与 `VMQ_MASTER_KEY_OLD`（默认空），在 `.env` 里填值即可生效；若使用自定义 compose 文件，需自行加入这两个变量。

### 4. 启动与核验

```sql
SHOW INDEX FROM orders;
-- 期望：存在 uq_orders_merchant_pay_id 与 idx_orders_merchant_state，且不再有 uq_orders_pay_id
```

- `GET /health`、`GET /ready` 正常；
- 用原生协议下单一次，确认 `merchant_id=0` 落库（管理台订单页会出现「系统商户」列）；
- 管理端登录正常；侧栏出现 **商户管理**，可创建商户并拿到一次性密钥；
- 监控端在线状态正常。

### 5. 常见报错

| 报错 | 原因 | 处理 |
| :--- | :--- | :--- |
| `orders 表不存在：请先用 -init-db 初始化基础表结构` | 顺序反了，或连到了空库 | 全新库先 `-init-db`；旧库确认 `VMQ_DB_NAME` 是否指错 |
| `orders 上既没有 uq_orders_pay_id 也没有 uq_orders_merchant_pay_id，请人工确认索引状态后再迁移` | 有人手工动过索引 | 按实际状态决定先建哪个索引，迁移器不猜 |
| `VMQ_FRONTEND_URL 必须显式配置...` / `VMQ_TOKEN_SECRET 必须...` | 新增必填项没补齐 | 对照 `env.production.example` 补齐；启动前校验，不会带病上线 |
| 建单报 `Unknown column 'merchant_id'` | 直接启动了新版本、没跑迁移 | 停服 → `-migrate` → 再启动 |

### 6. 回滚边界

- **加列可回滚**（`DROP COLUMN`），但会丢失 `merchant_id`，此后 EPay 订单无法正确签名；
- **索引切换不可回滚**：一旦已有两个商户使用相同 `out_trade_no`，重新加全局唯一索引必然 1062；
- 最稳妥的回滚方式是恢复升级前的备份。

## V3.6（EPay V2 开放）升级步骤

> **V3.6 没有 schema 变更**（`diff bf87e40..HEAD -- database/` 为空）。升级是纯二进制/镜像替换，
> 不需要跑 `-migrate`；老库直接换制品即可。

### 1. 升级前必须清点的一件事

V2 商户**只能**用 V2 协议下单。若回滚到 V3.5，V2 验签能力会整体消失，
这些商户会 100% 返回「签名错误」。升级前先确认：每个 V2 商户是否还持有开通时下发的 V1 共享密钥。

```sql
-- 只开 V2、没有 V1 密钥行的商户（回滚后无兜底）
SELECT m.id, m.merchant_no, m.name
FROM merchants m
WHERE EXISTS (SELECT 1 FROM merchant_keys k WHERE k.merchant_id=m.id AND k.protocol=2)
  AND NOT EXISTS (SELECT 1 FROM merchant_keys k WHERE k.merchant_id=m.id AND k.protocol=1);
```

### 2. 存量数据回填（仅升级前换过商户公钥的部署需要）

V3.6 之前「换商户公钥」只更新当前代，上一代残留旧公钥——旧私钥仍能签单。
升级后新代码只对**下一次**换钥生效，历史残留需要一次回填：

```sql
-- 把上一代的商户公钥对齐到当前代（V2 只有 protocol=2 使用 peer_public_key）
UPDATE merchant_keys prev
JOIN merchant_keys cur
  ON cur.merchant_id = prev.merchant_id
 AND cur.protocol   = prev.protocol
 AND cur.generation = 1
SET prev.peer_public_key = cur.peer_public_key
WHERE prev.protocol   = 2
  AND prev.generation = 0
  AND prev.peer_public_key <> cur.peer_public_key;

-- 核验：应返回 0 行
SELECT COUNT(*) FROM merchant_keys prev
JOIN merchant_keys cur
  ON cur.merchant_id = prev.merchant_id AND cur.protocol = prev.protocol AND cur.generation = 1
WHERE prev.protocol = 2 AND prev.generation = 0 AND prev.peer_public_key <> cur.peer_public_key;
```

### 3. 回滚边界

| 项 | 可否回滚 | 说明 |
| :--- | :--- | :--- |
| 二进制/镜像 | 可 | 换回 V3.5 制品即可，无需 schema 回滚 |
| V2 验签能力 | **不可** | V3.5 不含 V2 代码；V2 商户下单全部失败，只能切 V1 |
| 换商户公钥 | **不可** | 覆盖全部代且无历史列；回滚不恢复旧公钥，旧密钥永久作废 |
| 平台密钥轮换 | 部分 | 轮换一次可由上一代兜住；连续两次会删除最早一代 |

### 4. 升级后核验

1. `/health`=200、`/ready`=200（`/ready` 会真 Ping DB）；
2. 原生 `/api/order/create` 下一单，确认 `merchant_id=0`；
3. V1 商户下一单并核对回调；
4. V2 商户下一单，用平台公钥验证响应 `timestamp`+`sign`，并确认回调是 **POST form**。

## 版本升级通用步骤

1. 备份数据库：`mysqldump ... > backup-$(date +%F).sql`。
2. **先**比对 `.env` 与新版 `env.production.example`，补齐新增变量（如 V3.0 的 `VMQ_SERVER_*_TIMEOUT`、
   V3.4 的 `VMQ_MASTER_KEY`）。顺序不能反：先启动再补变量，中间那段就是宕机窗口。
3. 拉取新版本 / 替换二进制（或 `docker compose pull`）。
4. 涉及数据库结构变更时**先**执行迁移命令（V3.3 起统一为 `./vmqfox-api -migrate`，幂等），再启动服务。
5. 启动/更新服务（`docker compose up -d`）。
6. 校验 `/health`、`/ready`，登录管理台确认监控端在线状态正常。
